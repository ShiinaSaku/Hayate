Hayate splits a transfer into stages that run in parallel, so reading, hashing, compressing, encrypting and sending overlap.

```text
Disk → [8 async reads × 4 MiB] → [hasher thread] → [workers: zstd + AEAD] → [QUIC window] → Wire
                                                                                  ↓
                                    receiver: decrypt → reorder → hash → sequential write
```

## Pipeline

- **Read-ahead.** Up to eight concurrent 4 MiB reads keep the disk busy while cryptography runs.
- **Dedicated hasher.** BLAKE3 or SHA-256 runs on its own thread, so hashing large frames never stalls the async event loop.
- **Worker threads.** Compression and encryption run on dedicated threads connected by channels.
- **Bounded queues.** Every stage has a bounded queue. A slow disk or network applies backpressure instead of filling memory with buffered frames.
- **Cipher negotiation.** The receiver picks AES-256-GCM when the CPU has hardware AES, and ChaCha20-Poly1305 otherwise. Set `HAYATE_FORCE_CHACHA20` to force ChaCha20-Poly1305.
- **Adaptive compression.** zstd level 1 is skipped for already-compressed file extensions. Hayate also turns it off after 16 MiB if the data is effectively incompressible.
- **Ordered writes.** The receiver reorders frames before writing, so disk I/O stays sequential.

Hayate runs on [compio](https://github.com/compio-rs/compio), a completion-based async runtime that uses io_uring on Linux, IOCP on Windows and kqueue on macOS.

## Measure throughput

The repository includes a loopback benchmark. From a clone, run:

```bash
cargo run --release --example throughput -- ./large.bin 3
```

The example sends the file to a receiver in the same process over loopback, timing connect, handshake and payload together. The second argument is the number of rounds (default `3`). Set `HAYATE_BENCH_COMPRESS=0` to measure without compression.

Throughput depends heavily on whether the operating system supports UDP segmentation offload (GSO and GRO). Linux has both. macOS currently has neither, so the same pipeline moves far fewer packets per second there.

## Linux socket buffers

If transfers stall under load on Linux, raise the kernel's UDP buffer limits:

```bash
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728
```

These settings last until reboot. To keep them, add the same keys to a file in `/etc/sysctl.d/`.

macOS and Windows size UDP buffers automatically.
